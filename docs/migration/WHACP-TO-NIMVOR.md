# Migrating a server from WhaCP to NimVor

NimVor was called WhaCP until the project was renamed. The rename touched
everything: the system user and group, `/opt`, `/etc`, `/var/lib`, `/var/log`
and `/var/backups` folders, the systemd units, the `bin/` command, the
environment variables, the API headers, and the markers written into host
configuration files. There is **no compatibility layer**: a NimVor agent and
panel do not read the old names, and the NimVor installer refuses to run on a
server that still has `/opt/whacp`, `/etc/whacp` or `whacp-agent.service`, so
it can never end up half-installed beside the old panel.

This page is the plan for the one server that runs the former name. **Nothing
here has been run yet. Do not pull the new code on that server, run the new
installer, or delete anything until you have read this and decided.**

## What happens to what

| | Under the old name | After the rename | Needs migrating? |
|---|---|---|---|
| Websites, databases, mail, DNS, certificates | served by Nginx, PHP-FPM, MariaDB, … | unchanged; they do not depend on the panel to keep running | no, but the panel must learn about them again (step 7) |
| Panel program, config, database | `/opt/whacp`, `/etc/whacp`, `/var/lib/whacp/whacp.sqlite` | `/opt/nimvor`, `/etc/nimvor`, `/var/lib/nimvor/nimvor.sqlite` | yes |
| Services | `whacp-agent`, `whacp-panel`, `whacp-scheduler(.timer)`, plus greylist, DKIM, FTP, mail-rate, firewall units a profile installs | `nimvor-…` | yes |
| Files the agent wrote | `whacp-<domain>.conf` (Nginx, PHP-FPM), `whacp-acct<N>.slice`, `.whacp-quarantine` and `.whacp-trash` folders, `### whacp-run` cron markers, "Managed by WhaCP" headers, `whacp_*` nftables tables | `nimvor-…`, `.nimvor-…`, "Managed by NimVor" | regenerated by NimVor; old ones are cleaned up (step 9) |
| Backups made by the old agent | `/var/backups/whacp` | `/var/backups/nimvor` | the archives are plain files, but **the old backups fail NimVor's integrity check** (the key-derivation label contains the product name). Keep them as raw archives; take new backups after the migration |
| Browser sessions, "verified IP" codes | cookie `whacp_session` | `nimvor_session` | everyone signs in again once |
| Passkeys (WebAuthn) | user handle derived from the old name | derived from the new name | register passkeys again (password and TOTP keep working) |

## Step 0 — look before changing anything (read-only)

```bash
sudo bash docs/migration/whacp-inventory.sh | tee /root/whacp-inventory.txt
```

It lists the services, folders, host files, cron markers, database row counts
and websites the migration has to deal with. Send it back before step 4; the
choice between the two routes below depends on it.

## Step 1 — snapshot and backup

1. Take a **provider snapshot** of the VPS. This is the real rollback.
2. Copy the old checkout somewhere the new code cannot overwrite it. The old
   uninstaller (the only tool that knows every old name) lives in it:
   ```bash
   sudo cp -a ~/WhaCP /root/whacp-old-checkout
   ```
3. Archive the panel's own data:
   ```bash
   sudo systemctl stop whacp-scheduler.timer whacp-scheduler.service
   sudo tar -C / -czpf /root/whacp-premigration.tgz \
       etc/whacp var/lib/whacp var/lib/whacp-agent var/backups/whacp \
       $(ls -d var/lib/whacp-workers etc/whacp-* 2>/dev/null)
   sudo chmod 600 /root/whacp-premigration.tgz
   ```
   It contains the panel key and agent token: keep it private, off the server
   when you are done.

## Route A — recommended: remove the old panel, install NimVor, import the sites

The websites, databases, mail and DNS keep running throughout: the old
uninstaller removes only the panel's own units and files, never the services
it managed.

| # | Do | Why / what you notice |
|---|---|---|
| 2 | `cd /root/whacp-old-checkout && sudo ./installer/uninstall.sh` (no `--purge`) | Removes the old services, `/opt/whacp`, the jailed shell. Accounts that used the jailed SSH shell get `nologin` until step 7. Sites keep serving. |
| 3 | `sudo mkdir -p /root/whacp-premigration && sudo mv /etc/whacp /var/lib/whacp /root/whacp-premigration/` | The NimVor installer refuses to run while `/etc/whacp` exists. The data stays in the archive and here. `/var/backups/whacp`, `/var/lib/whacp-agent` and `/var/lib/whacp-workers` stay where they are, unused. |
| 4 | Merge the PR, then `curl -fsSL https://nimvor.com/install \| sudo bash -s -- --public-https --enable-writes` (or install from the branch while testing: add `--branch <name>`). Pin with `--commit <sha>` if you want. | Fresh NimVor under the new names. A new administrator is created; the panel opens on `https://SERVER-IP:8443`. |
| 5 | Run the setup wizard with the profile you used before, or skip it if the server is already configured | The wizard only fills in what is missing. |
| 6 | Sign in, check **Server → Components** and **Security** | |
| 7 | **Websites → Import**: import each discovered website | NimVor takes over the existing Nginx/PHP-FPM configuration (a preview of the new configuration is shown first) and rewrites it under the new names. Re-create databases, mail domains and DNS zones the same way (Discovery lists them). Re-apply SSH access for accounts that had the jailed shell. |
| 8 | Check every website in a browser, then mail and DNS | |
| 9 | Clean up the orphans the old names left (listed by the inventory): old `whacp-*.conf` Nginx and PHP-FPM files that are no longer enabled, `whacp-acct*.slice`, `.whacp-quarantine` / `.whacp-trash` folders, `whacp-worker-*` units still running next to the new `nimvor-worker-*`, old `whacp_*` nftables tables. Remove them **one group at a time, testing the sites in between**. | |

**Rollback of route A** (until step 9): restore the provider snapshot. Or, from
`/root/whacp-old-checkout`, put `/root/whacp-premigration/etc/whacp` and
`var/lib/whacp` back, remove the NimVor install, and run
`sudo ./installer/install.sh --reinstall` there.

## Route B — in-place rename

Renames the user, folders, units and host files of this one server instead of
reinstalling. It keeps the panel database, users and settings, but touches the
most files and cannot be rehearsed on a copy. I will write the exact script
for the server only after seeing the step 0 inventory, and it will have a
`--dry-run` that prints every rename. Use it only if the server holds data that
cannot be re-imported (many users, plans, DNS records).

## What I could not verify

* Neither route has been run on a real host: no server was available while
  writing this. The pieces are tested as follows: the agent and panel code
  under the new names by their unit and HTTP tests, the bootstrap script
  against a local git repository. The old uninstaller is unchanged from the
  version that has been running on the server.
* `docs/migration/whacp-inventory.sh` has not been run on a live host either;
  it only reads.
* The behaviour of **Websites → Import** on a site the old panel created is
  the part most worth testing first, on a single low-value site, before
  committing to route A.

After the migration, delete this folder's migration notes and
`docs/migration/whacp-inventory.sh`: they mention the old name on purpose.

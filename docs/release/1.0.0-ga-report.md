# WhaCP 1.0.0 — GA release audit

Audit of branch `claude/sleepy-ptolemy-bdv6ib` at commit `3b004c2` (the
code; this report is the next commit). No new features, no UI changes.
Classification: **CRITICAL** blocks GA, **HIGH** fix before GA, **MEDIUM**
after GA, **LOW** future.

## Findings

| # | Class | Area / scenario | Finding | Status |
|---|-------|-----------------|---------|--------|
| 1 | CRITICAL | Agent, scenario A (panel → root) | An existing Linux account in a privileged group (sudo, wheel, adm, docker, lxd, disk, shadow, …) or named in `/etc/sudoers`/`sudoers.d` could be adopted as a website account (`sites.apply` with an existing user) and every run-as-account path (PHP-FPM pool, cron, workers, deploy hooks, WP-CLI) would then run as it — root via its sudo rights. Path: `agent/internal/sites/sites.go` `ensureUser`, `agent/internal/host/env.go` `Credential`. | Fixed in `5a2dc26`: `host.PrivilegedAccount` (groups + sudoers parsing) refused in `Credential` and in `ensureUser`. Test `TestPrivilegedAccountsNeverRunWebsites` (sudo group, docker, sudoers user, User_Alias, `%group` in sudoers.d; comments, Defaults, Cmnd_Alias and dotted sudoers.d files do not trigger). |
| 2 | HIGH | Agent, ModSecurity source build | A pre-existing `whacp-build` account (or a website named so) was trusted by the source build; its processes could alter sources mid-build and the resulting module is loaded into Nginx's root master. Build outputs were read through symlinks, so a planted link could make root copy e.g. `/etc/shadow` into a world-readable file. Path: `agent/internal/modsec/source.go`, `agent/internal/txn/txn.go` `InstallFile`. | Fixed in `5a2dc26`: the account must be WhaCP's own (home + comment), the name is reserved for websites, outputs must resolve inside the build folder, `InstallFile` opens with `O_NOFOLLOW`, regular files only, 512 MiB cap. Tests `TestBuildAccountAndOutputsAreNotTrusted`, `TestInstallFileRefusesLinks`, `TestBuildAccountNameIsReserved`. |
| 3 | HIGH (defence in depth for #1) | SSH/SFTP/shell | `sftp.configure` / `shell.set` accepted any UID ≥ 1000 account whose home is under the sites root, including one with administrator rights. | Fixed in `d889486`; test `TestAdministratorAccountsGetNoAccess` (fails without the fix). |
| 4 | MEDIUM | Scenario H (concurrency) | `InstallCRS` read-modified-wrote the ModSecurity state without the actions' lock; a website mode changed meanwhile could be lost. No privilege impact. | Fixed in `02d0351`; test `TestInstallCRSWaitsForOtherStateChanges` (race detector on). |

No other CRITICAL or HIGH issue was found.

## Attack scenarios

- **A — compromised panel → root:** reviewed every privileged action added
  since rc1 plus the existing high-risk ones: terminal root gate (only
  `/etc/whacp/agent.json`, not writable by the panel), fail2ban jails
  allowlisted, SSH settings typed and `sshd -t`-checked, MariaDB and php.ini
  allowlists (no `auto_prepend_file`, `open_basedir`…), tmpfiles fixed
  content, mail routing enums and structured filters (no raw Sieve), worker
  and cron commands as the site account with `NoNewPrivileges`, DNS zones
  re-rendered (`$INCLUDE` dropped), `services.control` allowlist, backup
  remote validated, webmail host name validated and Roundcube config built
  from internal values only, firewall rules parsed into arguments,
  `ffmpeg.access` UID ≥ 1000 only. Findings #1–#3 fixed.
- **B — compromised site:** site folder `0710 site:www-data`, document root
  `0750`, per-site account and PHP-FPM pool, `/etc/whacp` `0750 root:whacp`
  with `0640` files, `/var/lib/whacp` `0750 whacp`, backups `0700 root`,
  agent socket `0660 root:whacp` + peer-UID allowlist + token; site
  restores extract as the site account.
- **C — IDOR/BOLA:** owner scoping on every site route (existing suites);
  new regression that another customer's trash list/restore/delete/empty
  return 404 and never reach the agent. Quota, bandwidth and ModSecurity
  install routes are admin-permission routes.
- **D — traversal/symlinks:** File Manager and trash confined by `os.Root`
  (a link race can only touch the attacker's own site); archive extraction,
  server restore, CRS unpacking, cron logs, disk usage and backups have
  hostile-entry tests; Git deploy disables `file`/`ext` protocols and hooks.
- **E — command injection:** no shell strings run as root; every `sh -c`
  runs as the website account; argument lists with `--`.
- **F — webhooks:** HMAC-SHA256 or GitLab token with `hash_equals`; replay
  refused by body hash (409, audited, notified).
- **G — auth:** Argon2id, throttling, TOTP/WebAuthn, session rotation —
  covered by the existing security suites (all green).
- **H — concurrency:** finding #4; install/rollback serialised by
  `installMu`, configuration by the web-config lock.
- **I — failures:** agent down/timeout/auth failure/malformed answers shown
  as server states (tests); new real-host test fills a tmpfs and confirms a
  failed write keeps the old file and leaves no temporary file.
- **J — upgrade/rollback:** see below.

## GA Release Report

- **Version:** 1.0.0 (tree `VERSION` still reads `1.0.0-rc1`; tag after CI runs)
- **Git commit:** `3b004c2` (audited code)
- **Supported OS:** Ubuntu 22.04, 24.04, 26.04 LTS; AlmaLinux / Rocky Linux 9 and 10 (SELinux enforcing)
- **CI results:** **not available.** GitHub Actions runs 182–185 for this branch end in ~3 s with no steps executed (no runner assigned: account/billing side, not a test failure). The last green CI run predates this audit.
- **Real-host test results (Ubuntu 24.04 container, root, no systemd):** 54 agent packages pass with `-tags realhost`; backup, dbmgr, redismgr, ftpmgr pass once MariaDB, Redis and sshd are started by hand. Not runnable here (need systemd as PID 1 or netfilter): execx transient units, workers, mail DKIM unit, UFW.
- **Security audit results:** 1 CRITICAL, 2 HIGH, 1 MEDIUM found; all fixed with regression tests. Agent: `go vet` (also `-tags realhost`), `go test -race` on changed packages, full `go test ./...` green. Panel: 361 PHPUnit tests, 3111 assertions, green. `make lint` green.
- **Upgrade test result:** pass — `UPGRADE_FROM=30d0776` (1.0.0-rc1) with realistic fixture data: failed migration rolled back files and database, good upgrade migrated and passed health checks, fixture data (users, websites, databases, backups, API token, encrypted secrets, audit history) intact, tampered upgrade backup refused.
- **Rollback test result:** pass — `--rollback` restored 1.0.0-rc1. ModSecurity installer rollback verified on a real build earlier (`8ddd5a4`).
- **Backup/restore result:** pass — real MariaDB: site files and database backed up, encrypted, restored (`TestRealHostBackupRestore`); server restore hostile-archive tests green.
- **Browser test result:** 16/16 Playwright (Chromium) test files pass.
- **Installation result:** `tests/integration/smoke.sh` passes (agent, doctor, panel, login, discovery, pinned remote TLS, fixture unchanged). A full `install.sh` on a systemd host was not run in this session.
- **Uninstallation result:** not executed in this session (needs systemd); script syntax-checked only.

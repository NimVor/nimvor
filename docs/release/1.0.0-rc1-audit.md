# WhaCP 1.0.0-rc1 — release-readiness audit

This is the working audit for taking WhaCP from the unreleased 0.5.0 to
1.0.0-rc1. It records what exists, how it is tested, what was found and
what was fixed. It is updated as work lands. "Tested" means an automated
test in this repository that runs in CI, unless stated otherwise.

Severity scale: **BLOCKER** (server compromise, cross-tenant data,
authorization bypass, privileged command execution, config/data loss,
unreliable restore, broken upgrade or installer), **CRITICAL**, **HIGH**,
**MEDIUM**, **LOW**, **INFO**.

## 5. F-16 — commands as a website account under the installed agent unit

### Reproduction

`tests/integration/postinstall.sh` after `installer/install.sh --enable-writes`
on the Ubuntu 24.04 runner (systemd 255, kernel 6.17): creating a backup of a
website failed with `fork/exec /usr/bin/tar: operation not permitted`. The
real-host tests did not see it (they run the agent outside systemd), nor did
AlmaLinux 9 (systemd 252). `tests/integration/sandbox-probe.sh` clones the
installed unit (base unit plus the write-mode drop-in) and runs the same
kinds of command as a website account under variants of it.

### Root cause

The failing step is not tar, seccomp, file permissions or any other sandbox
property: `setpriv --reuid=<site> --regid=<site> --clear-groups /usr/bin/true`
fails inside the cloned unit with `setresuid failed: Operation not
permitted`; changing only the group works; every other program fails the
same way. In the running agent, `/proc/<pid>/status` shows `CapBnd:
a90437ff` (the write-mode bounding set, including `CAP_SETUID`) but
`CapPrm`/`CapEff: a904377f` — `CAP_SETUID` missing. On this systemd, the
unit's process started without it in its permitted set, and with
`NoNewPrivileges=yes` the kernel never adds a capability back at `execve`
(file capabilities and setuid bits are ignored), so the agent could never
switch to another UID. The probe confirmed that only removing
`NoNewPrivileges=yes` made it work; that was rejected (it would let every
process the agent starts gain privileges through setuid binaries).

### Fix (architectural; the agent's unit is unchanged)

The agent no longer changes credentials at all. `execx.RunWith` with
`Opts.As` starts the command through `systemd-run --uid=<site> --gid=<site>
--wait` as a transient unit (`whacp-run-<random>.service`) that PID 1
creates, with:

`NoNewPrivileges=yes`, `CapabilityBoundingSet=` (empty), `RestrictSUIDSGID=yes`,
`ProtectSystem=full`, `ProtectKernelTunables/Modules/Logs=yes`,
`ProtectControlGroups=yes`, `ProtectClock=yes`, `RestrictRealtime=yes`,
`LockPersonality=yes`, `KillMode=control-group`, `TimeoutStopSec=5`,
`RuntimeMaxSec` (backstop after the agent's own deadline).

Standard input, output and error are named pipes in `/run/whacp-run/run-*`
(folder `root` 0711, pipes 0600 owned by the account), opened by a fixed
`sh -c 'exec "$@" <in >out 2>err'` wrapper that already runs as the account
(F-19 explains why neither D-Bus descriptor passing nor PID 1 can open
them on RHEL). Arguments are passed as separate `argv` entries after `--`;
`$` is escaped as `$$` because systemd expands variables in command lines.
The existing checks are unchanged: the allowlist (`systemd-run` was already
in it), `sh`/`tar` only as UID ≥ 1000, no control characters. Without
systemd (development containers) the old direct credential switch remains.

### Security analysis

| Question | Answer |
|---|---|
| Did the agent's sandbox change? | No. `whacp-agent.service` and `whacp-agent-write-mode.conf` are unchanged; `NoNewPrivileges=yes` is kept. `systemd-analyze security whacp-agent.service` on the installed Ubuntu runner: **5.8 MEDIUM**, the same as before the fix (with `NoNewPrivileges=` ✓). |
| What new capability does the agent use? | Starting transient units through `systemd-run` (D-Bus to PID 1), which it could already do as root (`systemctl`). The command, account and properties are fixed by `execx`; callers cannot add properties. |
| Can the site command gain privileges? | No: empty bounding set, `NoNewPrivileges`, no setuid/setgid. The real-host test reads `/proc/self/status` inside the unit: `CapEff` and `CapBnd` zero, `NoNewPrivs: 1`. |
| Can it escape its account or change the system? | It runs with the account's UID/GID only; `/usr`, `/boot`, `/etc` are read-only (`ProtectSystem=full`); writing `/etc` fails (tested in the real-host test and, through the installed service, by the post-install cron "run now" check). |
| Can it outlive its timeout? | No: the agent stops the unit (`systemctl stop`) at its deadline, `KillMode=control-group` kills every process in it, `RuntimeMaxSec` is a backstop. Tested (no process left after a 2 s timeout). |
| Can the account attack the agent through the pipes? | No (F-21): the pipe folder is root's; the agent opens pipes with `O_NOFOLLOW` and only if they are pipes. Other accounts cannot list `/run/whacp-run` nor open another account's pipes (0600). |
| Tenant isolation | Unchanged: the account is derived from the website's owner by the agent (`Credential`, UID 1000–59999 only), never from the request. |
| Auditability | Each command is a named unit in the journal (`whacp-run-*.service`) with its account; the agent's job log keeps the output. |
| Mail from these commands | Local `sendmail` (setgid `postdrop`) cannot work under `NoNewPrivileges`; inside these units `sendmail` is WhaCP's SMTP submitter instead (F-25), with no added privilege. |

### Regression coverage

- `execx.TestTransientArgs` — account, `StandardInput=null`, every hardening
  property, no `StandardOutput/StandardError` opened by PID 1, argument
  escaping.
- `execx.TestTransientStreams` — 3 MB binary round trip through the pipes,
  stderr, exit status, a unit that fails to start does not hang the agent,
  nothing left behind; `TestOpenPipeRefusesLinksAndFiles`.
- `execx.TestRealHostCommandsAsAccount` (real systemd, Ubuntu and AlmaLinux)
  — UID/GID, zero capabilities, `NoNewPrivs`, `/etc` not writable,
  arguments with `$ % " '` and newlines, binary tar backup and restore
  with ownership, exit status, the account cannot plant a link or move a
  pipe, timeout stops the unit. It fails at once if the runner stops using
  transient units.
- `tests/integration/postinstall.sh` through the **installed** agent
  service: encrypted backup, damage, restore of files and database, and
  cron "run now" (as the site account, `CapEff` zero, cannot create
  `/etc/whacp-cron-escape`). This is the test that found F-16; it passes on
  Ubuntu 24.04 and AlmaLinux 9.

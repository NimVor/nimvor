# WhaCP 1.0.0 — GA production-readiness audit

A strict review of 1.0.0-rc1 before calling it 1.0.0, done on the code
and on the existing test suites (not on design intent). Every answer below
cites the code or the test that supports it; where no test exists, it
says so. Findings are ranked at the end (A–E).

Evidence base: branch `claude/sleepy-ptolemy-bdv6ib`; CI (agent unit
tests with `-race` and unprivileged, panel PHPUnit on PHP 8.3/8.4, smoke,
upgrade/rollback, Playwright, real-host tests and install + post-install
through the installed services on Ubuntu 24.04 (runner) and in VMs).

## 1. Installation

- **Idempotent?** Partly, by design. A second `install.sh` on an installed
  server refuses ("already installed … use upgrade.sh"); `--reinstall`
  repeats every step while keeping `/etc/whacp` (token, panel key,
  configuration) and the database. Every step inside is idempotent (user,
  directories, token and key only created when missing, `migrate`,
  first administrator only when there are no users).
- **Interrupted?** Nothing outside WhaCP's own files is touched by the
  installer: it never edits Nginx, PHP-FPM, Postfix, Dovecot, BIND,
  firewall or SELinux configuration (those are only changed later by the
  agent, in write mode, one validated change set at a time). An
  interruption during `--install-deps` leaves the package manager in its
  own recoverable state (`dpkg --configure -a` / `dnf`). An interruption
  after `/opt/whacp` or `/etc/whacp` exist makes the next plain run refuse
  with a message pointing to `upgrade.sh`, which in turn refuses if the
  installation is incomplete. The recovery is `install.sh --reinstall`,
  which the message does not mention (**B-3**).
- **`--dry-run`** prints every change through the same `run` wrapper
  (packages, user, directories, files, configuration, units, services,
  migration). It does not print the administrator creation or the health
  checks (no changes) and still asks the write-mode question unless
  `--yes`.

## 2. Upgrade / rollback

- `upgrade.sh` checks the new agent against the existing configuration
  before touching anything, then backs up the panel files, agent binary,
  units and drop-ins, `/etc/whacp` and the SQLite database (panel and
  scheduler stopped, WAL checkpointed), swaps files, migrates and
  restarts; any failure restores the backup automatically. Tested by
  `tests/integration/upgrade.sh` (failed migration rolls back files and
  database; good upgrade; `--rollback`), including from real 0.5.0 data.
- **Migration failing halfway:** each migration runs in a transaction
  (`Migrator`), and the whole database file is restored from the backup.
- **Service configuration invalid after upgrade:** an upgrade does not
  rewrite Nginx/PHP/mail/DNS configuration; the agent regenerates it only
  when an action changes it, and validates and rolls back then.
- **Rollback scope:** restores application state (files, database,
  configuration, units). It does not undo system configuration the new
  version wrote for later actions — document this (**B-9**). `--rollback`
  after a successful upgrade also discards panel data written since the
  upgrade (websites created meanwhile stay configured on the server but
  vanish from the panel) — the prompt must say so (**B-4**).
- **Backups versioned, verified?** Versioned (timestamp + version, last 3
  kept). Not verified: no `PRAGMA integrity_check` on the copied database
  (**B-4**).
- **Upgrade vs. running jobs** (**A-2, fixed**): `upgrade.sh` asks the
  running agent for queued and running jobs (`whacp-agent -wait-jobs`) and
  waits up to `--wait` (30 min) before changing anything, and again after
  the panel and scheduler are stopped; if jobs are still running it stops
  with nothing changed. Independently, a stopping agent refuses new
  requests, lets running jobs finish (5 min) and only then exits; its unit
  uses `KillMode=mixed` so a job's commands are not sent SIGTERM with it
  (anything left is still killed at `TimeoutStopSec`). Tested: wait,
  timeout, no agent, refused token (unit); drain and timeout of the job
  manager (unit); upgrade from 0.4.0 checks jobs and refuses a bad
  `--wait` (integration). Not tested: an upgrade during a real multi-minute
  restore on a VM (**E**).

## 3. Existing-server safety

- Every agent write goes through `agentfs.Policy`, an allowlist of the
  exact files and subtrees WhaCP owns (`whacp-*` vhosts and pools, its
  own directories). Tested by the adversarial writer tests.
- Configuration WhaCP did not create is only changed with an explicit
  flag the UI asks for: `confirm_edit_package_config` (12 actions: e.g.
  Postfix/Dovecot main configuration, Rspamd local.d files it did not
  write), `confirm_replace_service` (7), `confirm_replace` (2). Existing
  vhosts, pools, zones, firewall rules and Redis settings are discovered
  read-only; importing a website copies it into a new WhaCP site and
  disables the old vhost only in one validated reload, with undo.
- Ownership and permissions of replaced files are kept (F-17), and the
  SELinux label is kept (F-03). Tested (`TestKeepPreservesOwnerOnReplace`,
  real-host DNS on RHEL).

## 4. Privileged agent

- 156 named actions (92 mutating, refused unless write mode). The HTTP
  API is `POST /v1/actions/<name>` only; unknown names are refused; bodies
  are limited to 4 MiB and must be valid JSON; every action decodes into a
  struct with unknown fields refused (`host.Decode`).
- **No arbitrary execution:** the agent runs only allowlisted binaries by
  id (`execx.defaultCandidates`); arguments never pass through a shell;
  NUL/CR/LF are refused; `sh` and `tar` may only run as an account with
  UID/GID ≥ 1000 (`checkArgs`, tested). The only `sh -c` scripts are fixed
  strings with arguments passed positionally, or the customer's own cron
  command run as their own account.
- **Injection / traversal / option injection:** identifiers are validated
  (`validate` package) before use; paths resolve inside `filesystem.Root`
  (`os.Root`) and the write policy; positional arguments follow `--` where
  a tool supports it. The file manager and archive extraction were tested
  with 22 hostile paths × 15 operations.
- **Through the panel:** the agent token is on disk readable by the
  `whacp` group only; every panel route that calls the agent is behind
  authentication, a permission (RBAC matrix test) and ownership scope
  (tenant isolation tests).
- **Symlinks and races:** the writer refuses symlinks in owned subtrees;
  the file manager uses `os.Root`; the named pipes of site-account units
  are opened with `O_NOFOLLOW` in root-owned directories (F-21, tested).
- **Concurrency:** managers with shared state serialize their mutating
  actions with their own lock (mail, DNS, FTP, security, backups). Actions
  that touch per-site files (sites, pools, cron, workers) are not
  serialized with each other; two concurrent website changes could have
  one `nginx -t` see the other's files mid-change (worst case: a spurious
  rollback). Not proven either way by a test (**B-10**).

## 5. Website isolation

- Site root `0710 <site>:<web group>`, document root `2750`, logs/tmp/
  backups `0750` owned by the site account: no other account can enter.
  PHP-FPM runs one pool per site as the site account with `open_basedir`
  = the site root (plus `/usr/share/php`), its own temp and session
  directories; `disable_functions` when "harden" is on.
- A site account cannot reach `/etc/whacp` (0750 root:whacp),
  `/var/lib/whacp`, `/run/whacp` (agent socket, 0750), `/var/backups/whacp`
  or `/var/lib/whacp-agent` (0700 root).
- Commands WhaCP runs as the account (backups, restores, cron "run now",
  deploy hooks, app installers) run in transient units: its UID/GID only,
  empty capability set, `NoNewPrivileges`, read-only system, timeouts —
  **verified as enforced** by reading `/proc/self/status` inside the unit
  on Ubuntu and AlmaLinux (real-host and post-install tests), not only
  configured. `RestrictSUIDSGID` was removed from these units (Ubuntu
  26.04: its seccomp filter breaks tar's `openat2`); extracted archives
  have setuid/setgid bits stripped (tested).
- The file manager cannot leave the site: `..`, symlinks, archives
  (zip/tar entries, links, absolute paths, bombs), uploads, rename/move
  and the editor are covered by the adversarial sweep.
- Customer background workers still use `RestrictSUIDSGID` and may hit
  the same `openat2` failure on Ubuntu 26.04 (**B-8**).

## 6. Database security

- The SQL console and browser connect as a per-database account that is
  locked between requests (password rotated each time); results are
  limited (1000 rows, 16 MiB, 1 MiB queries). Routes require
  `databases.manage` and ownership (tenant isolation test).
- Grants and host patterns are validated; deletion requires typing the
  name. Stored database passwords are encrypted with the panel key and
  shown only on request.
- Restores of database dumps run the `mysql` client as the database
  superuser without the client's sandbox option. The known mysqldump
  newline injection (customer-controlled table names) was tried here on
  MariaDB 10.11.14 and is **not** exploitable (mysqldump comments the line
  and writes the sandbox marker); servers with unpatched pre-2024 clients
  would be exposed. Defense in depth: **B-2**.
- Backups a customer stores on their own destination cannot be edited to
  inject SQL: manifests (with SHA-256 per file) stay on the server and
  every downloaded file is verified.

## 7. Authentication

Tested: password reset (hashed single-use tokens, expiry, throttling,
same answer for unknown accounts); session regeneration on login
(fixation); `HttpOnly`, `Secure`, `SameSite=Lax` cookies, cookies only;
password change and disabling a user end other sessions; idle and
absolute timeout; lockout after repeated failures (by user and IP);
TOTP with replay protection and single-use recovery codes; WebAuthn
(ES256/RS256/Ed25519, counters, origin/RP checks); role-required 2FA;
CSRF on every POST (middleware; tests for the generic case, plugins and
the webhook exemption). The notifications count poll does not count as
activity (tested).

## 8. Authorization / multi-tenancy

- RBAC: every route × every default role without its permission → 403
  and no agent call (`RbacMatrixTest`).
- IDOR/BOLA: every `/sites/{id}` route, databases, mail, DNS, backups,
  certificates, logs, cron, workers, deployments (web and API), jobs and
  notifications are refused across tenants (`TenantIsolationTest`,
  `ApiIsolationTest`, `ScopingTest`, `NotificationsTest`). Audit records
  and other users' API tokens are not reachable by customers (routes
  require `audit.view`; tokens are listed per user only).
- Plugin routes use the same router, authentication, CSRF and permission
  checks (tested); row-level scope inside a plugin is the plugin's own
  code (trusted, administrator-installed — documented, F-08).

## 9. API

Tested: read-only tokens cannot write (403 on every non-GET), deleted,
expired and malformed tokens are refused immediately, 120 requests/minute
per token, no session is created, secrets are not returned (database
passwords only when explicitly revealed in the UI). **Not tested:** that
`openapi.yaml` matches the routes (**E**).

## 10. Email

Tested on real Postfix/Dovecot/OpenDKIM/Rspamd (Ubuntu and AlmaLinux):
submission on 587 needs authentication and STARTTLS; a user cannot send
as another mailbox (`reject_sender_login_mismatch`); no open relay on 25;
DKIM signature present; GTUBE rejected, spam filed to Junk; IMAP only
over TLS, wrong password refused; Roundcube runs in its own pool and
account, signs in and sends through submission. SPF/DKIM/DMARC records are
generated for the zone. **Not tested:** that a full mailbox refuses
delivery (quota is configured) (**E**).

Found by CI during this audit: on AlmaLinux 9 a GTUBE message was accepted
right after the spam filter was turned on. `postfix reload` only signals
Postfix's master; an smtpd started before it can take the next connection
with the old settings. Reproduced locally (Postfix 3.8, a changed banner
checked on the first connection after `postfix reload`): old settings in
7 of 141 rounds. Fixed: the agent now returns only after the smtpd
processes from before the reload have exited — 0 of 144 rounds, at most
15 ms longer (**A-4, fixed**). Also found: deleting a mailbox or website
left its data in place when it was on another disk than
`/var/lib/whacp-agent` (rename across filesystems); the trash is now on
the data's own disk (**A-3, fixed**).

## 11. DNS

Every change runs `named-checkzone` / `named-checkconf`, is loaded, and
is verified by querying the new SOA serial; failures roll back (tested on
Ubuntu and AlmaLinux; F-17 found and fixed there). Records are validated
(2000 per zone). Zone transfers are allowed only to the configured
secondaries, which are notified. **Not tested:** an AXFR from a
non-secondary being refused (**E**).

## 12. Backups

Tested: AES-256-GCM encryption; tampered, truncated, wrong-key and
checksum-mismatched backups are refused before anything is changed;
restore of files and database with a safety backup first; SFTP/FTPS
remote round trips; interrupted downloads leave `.partial` files that are
removed; server configuration restore validates and rolls back
(`TestRealHostServerRestoreDrill`). The backup key lives in
`/var/lib/whacp-agent` and is never inside a backup; the docs tell
administrators to keep a copy off the server. **Gaps:** server backups
(which contain `/etc/whacp`: the agent token and the panel key, and TLS
private keys) may be made unencrypted (**B-5**); no free-space check
before a backup or restore (**B-6**); "restore into a clean server" is
documented but not tested end to end (**E**).

## 13. Secrets

No private keys, tokens or credentials in Git outside test fixtures
(release archives exclude tests and are scanned before publishing).
Agent logs and error details pass through `logging.Redact`; the panel's
audit details through `Redactor`; notification bodies are redacted and
truncated (tested with an injected password and token); API errors never
contain internal details (tested). Files: `/etc/whacp` 0750 root:whacp,
`agent.token`, `panel.key`, `agent.json`, `panel.php` 0640 root:whacp,
backup key 0600 root. Browser storage holds only the theme choice.

## 14. Concurrency

- Same target (website, database) background jobs are serialized
  (`jobs.Manager` per-target lock).
- Two administrators editing the same website: the panel writes in
  SQLite transactions; the agent applies each change set atomically;
  mail, DNS, FTP, security and backup actions are serialized by their
  own locks; website/pool changes are not (**B-10**).
- Two backups of the same site queue behind each other; different sites
  run in parallel.
- Upgrade vs. jobs: the upgrade waits for running jobs and refuses to
  proceed while they run; a stopping agent drains jobs (**A-2, fixed**).
- The same action requested twice: jobs are not de-duplicated (a second
  backup is simply a second backup); webhooks are de-duplicated (F-05).

## 15. Failure recovery

Tested: invalid Nginx configuration → rollback (site lifecycle); BIND
reload failure → rollback (DNS); Postfix without TLS → rollback (mail);
unreachable remote storage → clear error; agent unreachable → friendly
message, no leak (panel tests). **Not tested:** PHP-FPM failing to
reload, Redis down during a change, disk full, read-only filesystem,
panel database unavailable, network down during an upload (**E**). By
design each change set restores the previous files and reloads on
failure, so the expected outcome is "reported, nothing worse", but it is
not proven for these cases.

## 16. Monitoring and notifications

Alerts are keyed by rule and subject: an open alert is updated, not
re-sent; resolution is sent once. Notifications are recorded once per
dedupe key; refused webhooks at most hourly; an agent outage is one
alert. Scope is enforced when reading (tested for admin, reseller,
customer, unrelated customer, owner change). The alert webhook is an
unsigned JSON POST without retries (the URL is the secret, as for
Slack/Mattermost) (**C**). Retention: notifications 90 days, metrics 30
days, resolved alerts 90 days; panel job history, deployment history and
the audit log grow without limit (**B-7**).

## 17. Resource exhaustion

Limits: agent request body 4 MiB, command output 1 MiB, archive
extraction 50 000 entries / 8 GiB, file manager listings 5000 entries,
editor 2 MiB, log views 5000 lines, SQL results 1000 rows / 16 MiB, DNS
2000 records per zone, application downloads 200 MiB, sendmail messages
64 MiB, notifications 1000 per website; panel scale test: 100 websites,
500 domains, 10 000 notifications, every page < 15 ms. **Not measured:**
millions of files in one site (backup and usage measurement stream, but
time is unbounded), very large databases (streamed), many mailboxes,
concurrent users (**E**).

## 20. Documentation needed before GA

Present: supported systems, installation, write mode, upgrade and
rollback commands, security model, agent architecture, backup key
handling, plugin trust model. **Missing:** minimum hardware; one table of
required ports (panel 8090 local, 80/443, 25/587/993, 53, 21 + passive
range, 22, agent 8443 remote); DNS and mail prerequisites (PTR, MX, SPF
for the host name, port 25 outbound); what uninstall leaves (websites
keep running; `/var/lib/whacp-agent` with the backup key and
`/var/backups/whacp` are kept even with `--purge`); what rollback does
not undo; a recovery procedure (restore on a new server); resource limits
(above); known limitations (Redis < 6.2 channels; Ubuntu 26.04 webmail;
Let's Encrypt only tested with a stand-in) (**B-9**).

## B. Should fix (before or soon after 1.0.0; each is a bounded change)

- **B-1** *(withdrawn after verification; now C)* The draft said customers
  could make the server connect to internal addresses through backup
  destinations. They cannot: every storage route (add, confirm, trust,
  Google callback, delete) requires server-wide scope, there is no API
  for storages, and a customer cannot even send backups to an existing
  storage. Now covered by a test. Administrators and operators may point
  a destination at an internal host on purpose (a NAS), so no address
  filter was added.
- **B-2** Database restores run the `mysql` client as the superuser without
  `--sandbox`/`--binary-mode`; not exploitable with current clients (tested
  on MariaDB 10.11), defence in depth for old ones.
- **B-3** The "already installed" message does not mention
  `install.sh --reinstall`, the recovery for an interrupted install.
- **B-4** Upgrade backups are not verified (`PRAGMA integrity_check`), and
  `--rollback` does not warn that panel data written since the upgrade is
  discarded.
- **B-5** Server backups can be made unencrypted although they contain
  `/etc/whacp` (agent token, panel key) and TLS private keys.
- **B-6** No free-space check before a backup or a restore.
- **B-7** Panel job history, deployment history and the audit log are kept
  without limit.
- **B-8** Customer background workers still use `RestrictSUIDSGID` and may
  hit tar's `openat2` failure on Ubuntu 26.04 inside a worker.
- **B-9** Documentation gaps: minimum hardware, one ports table, DNS/mail
  prerequisites, what uninstall leaves (backup key, backups), what
  rollback does not undo, restore-on-a-new-server procedure, limits, known
  limitations.
- **B-10** Changes to different websites are not serialised against each
  other (worst case: a spurious rollback when two `nginx -t` overlap).

## C. Safe as is / future

- Alert webhook is unsigned and has no retries (the URL is the secret,
  like Slack/Mattermost webhooks).
- GitLab webhook tokens are compared, not HMAC-signed (GitLab's own model);
  replay is refused (F-05).
- Plugins run with the panel's rights (administrator-installed, documented).
- A bundled PHP for the panel and webmail (would lift the Ubuntu 26.04
  webmail limitation) — only with a PHP security-release process.
- Jobs are not de-duplicated (a second backup is a second backup).
- An operator (staff, below administrator) can make the agent open TCP
  connections to internal addresses through a backup destination and learn
  whether a port answers. Response bodies are not shown (S3 errors are
  reduced to code and message; SFTP/FTP go through curl and ssh-keyscan),
  and plain-http cloud metadata endpoints are refused by the https rule.
  Low risk for a staff role that already manages services.
